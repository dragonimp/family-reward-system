## 2. 目标与现状结论

目标是降低儿童手表端对识字能力的依赖，让孩子能快速回到首页、凭图形辨认积分申请事项、直观理解排行榜，并有更多符合儿童偏好的表盘可选。

REQ-035 与 REQ-030 的菜单重构属于同一功能点，且当前主分支已经提前实现了大部分界面效果。因此后续实施应以差距修正和回归验证为主，避免重新设计导航或重复增加接口。

| 需求能力 | 基线代码现状 | 分析结论 |
| --- | --- | --- |
| 功能菜单返回首页 | 菜单标题栏已有 `id="home-menu"` 的房屋按钮，`aria-label="返回首页"`，点击执行 `setView('home')` | 已具备，需补交互/真机验证 |
| 每个积分申请事项使用不同小图标 | 规则列表使用 8 个 emoji 按数组下标循环分配 | 部分具备；超过 8 条会重复，排序变化会换图标，也未保证图标语义与事项一致 |
| 美化积分排行榜 | 已有鼓励横幅，前三名分别使用奖杯、银牌、铜牌，其他名次使用星星，并区分前三名卡片配色 | 已具备，需补空榜、长榜和当前孩子标识验证 |
| 增加儿童喜欢的表盘 | 在原有 3 款基础上已有“恐龙乐园、彩虹糖果、宇宙探险”，当前合计 6 款 | 已具备，需验证保存、重载、对比度和小尺寸显示 |

因此，`TASK-093` 可在本文提交后关闭；`REQ-035` 暂不能仅凭现有静态代码关闭，至少还需完成事项图标的稳定唯一策略、自动化验证及目标手表真机验收。

## 3. 详细产品与交互口径

### 3.1 功能菜单返回首页

1. “返回首页”控件只出现在功能菜单页标题区，使用房屋图形并保留可访问名称“返回首页”。
2. 点击后直接显示积分首页，不经过任何二次确认，不重新绑定设备，也不清除当前设备令牌。
3. 控件触控区域不小于 36×36 CSS 像素；图形、边框与背景在全部表盘主题上保持足够对比度。
4. 功能子页面的“返回菜单”继续返回菜单页，不改成直接返回首页，以保持导航层级稳定。
5. Android 系统返回键仍按“子页面 → 菜单 → 首页”的层级回退；菜单页的房屋按钮是儿童可见的显式快捷入口。

### 3.2 积分申请事项图标

图标的主要作用是帮助识字能力有限的孩子识别事项，不能仅做随机装饰。实现应满足：

- 同一次展示的每个启用事项具有不同图形，不允许因固定 8 个图标循环而在列表内重复。
- 同一规则在刷新、重新登录或规则排序变化后仍显示同一图标，不能继续按数组下标分配。
- 优先按规则名称或分类映射儿童易懂的语义图形，例如阅读/学习、写作业、刷牙、整理、运动、帮助他人、早睡早起、吃饭；无法识别的事项再按稳定规则 ID 分配通用图形。
- 图标必须与事项文字同时出现，不能仅依赖颜色传达含义；图标容器保持一致尺寸，避免 emoji 字体差异挤压文字。
- 当启用事项数量超过内置图形池时，应扩展图形池或组合不同图形底纹；不能静默回绕产生重复图标。
- 首期可在前端实现确定性图标解析，不要求数据库迁移。若产品后续要求家长自行选择图标，应另行扩展规则模型、规则编辑页和 API 字段。

建议解析优先级为“明确规则图标字段（未来）→ 名称/分类关键词 → 稳定规则 ID 分配”。实现时应将图标键与视觉渲染分离，便于后续将 emoji 替换为仓库内联 SVG，同时避免依赖 CDN 或外部字体资源。

### 3.3 排行榜视觉

1. 页面标题保持“好友积分榜”，顶部使用奖杯和积极鼓励文案，不出现贬低末位儿童的提示。
2. 第一、二、三名分别使用奖杯、银牌、铜牌或领奖台视觉；第四名以后保留清晰名次数字，不应全部只显示同一个星星而隐藏实际名次。
3. 每行显示名次、姓名、积分；当前孩子显示“我”标识。姓名过长时省略，但积分和名次不得被挤出。
4. 空榜显示“暂无排行”和鼓励添加好友的中性提示；只有一人时也正常展示冠军样式。
5. 排名视觉不改变 `GET /api/watch/friends` 的排序与数据口径，不新增奖励、扣分或公开排行榜逻辑。

### 3.4 儿童表盘

本期以当前 6 款作为最低交付集合：我的世界、HelloKitty、星光梦可、恐龙乐园、彩虹糖果、宇宙探险。新增表盘应满足：

- 每款在选择列表中有名称和缩略色块，选中状态明确；点击后继续复用 `PUT /api/watch/settings` 保存。
- 切换后首页、菜单、申请、排行榜等全部面板文字可读，尤其深色表盘需检查标题、状态时间、输入框和按钮对比度。
- 页面重载、设备重新打开和家长虚拟手表预览均显示已保存表盘。
- 在 194×368、240×240、320×360、466×466、368×194 代表性视口中不裁切关键内容。
- 不使用未经授权的角色图片或外部素材；当前主题名称和 CSS 图形可作为首期实现，正式上架前仍需完成名称/素材合规复核。

## 4. 技术影响与实现建议

- 主要影响 `FamilyReward.Api/Program.cs` 中 `/watch` 返回的 HTML、CSS 和 JavaScript；现有手表接口足以支持本需求，不预计新增数据库表或后端路由。
- 将当前 `ruleIcon(index)` 改为以规则稳定 ID、名称和可选分类为输入的解析函数。渲染前先为当前规则集合分配图标并检测碰撞，确保当前列表唯一。
- 排行榜第四名以后应同时显示名次数字；前三名图标只是名次的视觉增强，不应替代机器可读文本。
- `watch-app/scripts/verify-watch-app.mjs` 中现有儿童友好断言标记为 `REQ-034`，与本次 Orbit 需求编号 `REQ-035` 不一致。实施任务应更正测试标签并新增行为级断言，避免以后证据关联错误。
- 静态字符串包含检查只能证明元素存在，不能证明点击返回、图标唯一、设置持久化或小视口可用。建议抽出纯函数测试图标分配与名次渲染，并保留目标设备手工验收。
- Android 壳无需新增权限；本需求不得借机改变生产部署、设备认证、麦克风权限或解绑流程。

## 5. 验收标准

1. 已绑定设备进入功能菜单后，点击房屋图形立即回到积分首页；设备令牌和当前绑定状态保持不变。
2. 194×368、240×240、320×360、466×466、368×194 五组视口中，返回首页控件可见、可点击且不被圆形表盘裁切。
3. 准备至少 10 条启用积分规则时，当前列表每条规则图形均不同；刷新和调整规则顺序后，同一规则的图形保持不变。
4. 学习、刷牙、家务、运动、礼貌/助人等常见事项显示语义可理解的图形；未知事项也有稳定的非空图形和文字标签。
5. 排行榜前三名具有奖杯/奖牌视觉，第四名以后显示真实名次，当前孩子有“我”标识；0、1、3、10 人数据均无错位或裁切。
6. 表盘设置至少展示 6 款主题；逐一切换后保存成功，刷新页面仍保持所选主题。
7. 六款表盘下首页、菜单、积分申请和排行榜的文字、按钮与状态信息均清晰可读，深色主题不出现低对比度文字。
8. 图标和表盘不依赖外网资源，不使用颜色作为唯一信息表达方式，并通过可访问名称或邻接文字表达含义。
9. `node watch-app/scripts/verify-watch-app.mjs`、`dotnet build FamilyReward.Api/FamilyReward.Api.csproj` 以及新增的图标/导航自动化检查通过。
10. 在目标小天才、小米、华为手表至少覆盖实际计划发布的平台完成菜单返回、10 条事项、排行榜和 6 款表盘真机回归；生产发布只能由受控部署任务执行。

## 8. 待确认项与非阻塞说明

- 需产品确认“每个事项不一样”是要求当前启用列表内唯一，还是要求整个规则生命周期全局唯一。本文采用可落地且符合儿童识别目标的“当前列表唯一、同一规则稳定”口径。
- 需确认实际首发平台和最低系统版本，以确定 emoji 渲染是否一致；如差异明显，应统一切换为仓库内联 SVG 图标。
- `HelloKitty` 等名称可能涉及第三方商标或角色形象。当前实现仅使用名称和 CSS 色彩，但正式市场上架前仍应由发布资料负责人确认命名合规；该确认不阻塞需求分析任务。
- Atlas MCP 未提供，无法额外核对 Atlas 公约、环境、关联事项或写回证据；Gateway 可依据本次结构化结果同步。
