## 2. 现状与差距

当前 `/watch` 已有单个右侧“菜单”按钮，但点击后会在右侧展开“积分、申请、记录、好友、设置、设备”六个圆形按钮；这不是需求所述的独立菜单页面。已有能力与需求的映射如下：

| 需求能力 | 当前能力 | 差距 |
| --- | --- | --- |
| 右侧只保留“菜单” | 收起状态只有一个菜单按钮，展开后出现六个按钮 | 点击后应进入表盘内的菜单页，右侧始终只显示一个菜单入口 |
| 所有菜单平铺并带形象图标 | 菜单是无图标的文字按钮 | 需建立带图标的菜单卡片/宫格，不使用二级折叠菜单 |
| 积分申请 | 已有申请表单和规则快捷项 | 需从菜单页进入；增加语音转文字和常用申请项图标 |
| 积分详情 | 首页展示余额，另有最近申请页 | 需定义独立详情页，至少汇总积分余额与最近申请状态 |
| 添加好友 | 当前好友页混合好友码、添加、好友列表和排行 | 需拆成独立入口，保留好友码生成与输入能力 |
| 排行榜 | 当前与好友页混排 | 需拆成独立入口和页面 |
| 表盘设置 | 已有三款表盘设置 | 只调整入口和菜单图标，保存逻辑可复用 |
| 设备绑定 | 绑定前有认证码页，绑定后“设备”页负责查看与解绑 | 菜单文案统一为“设备绑定”；已绑定状态下展示绑定信息和安全解绑，不重复执行绑定 |

## 3. 交互与信息架构

### 3.1 导航规则

1. 设备绑定成功后，首页保持当前视觉和数据内容不变。
2. 右侧只显示一个带图标和“菜单”文字的入口；任何页面都不在右侧展开其他功能键。
3. 点击“菜单”后，在表盘内容区打开菜单页。菜单页按“积分、好友、设置”分组展示，但所有六个叶子功能一次平铺可见，不再点击分组进入二级菜单。
4. 六个叶子功能为：积分申请、积分详情、添加好友、排行榜、表盘设置、设备绑定。每项包含形象图标和文字标签，整个卡片均可点击。
5. 子页面提供统一的“返回菜单”；再次按右侧“菜单”直接回到菜单页。Android 系统返回键优先退回菜单页，再退回首页，最后才退出 WebView。
6. 首页不得因菜单重构改变姓名、积分、现金、物品、表盘背景或首次加载行为。

### 3.2 图标口径

建议使用仓库内联 SVG 或 CSS 图标，避免引入网络图标库：积分申请使用“星星/加号”，积分详情使用“奖牌/账单”，添加好友使用“双人/加号”，排行榜使用“领奖台”，表盘设置使用“手表/画笔”，设备绑定使用“链环/盾牌”。

图标必须满足：

- 与文字一起显示，不能只靠颜色表达含义；
- SVG 使用 `aria-hidden="true"`，按钮保留完整可读文字或 `aria-label`；
- 触控区域不小于 36×36 CSS 像素，并在 194×368、240×240、320×360、466×466、368×194 代表性视口中不被表盘裁切；
- 不依赖外部字体、CDN 或运行时图片请求。

## 4. 各功能详细口径

### 4.1 积分申请

- 复用现有 `GET /api/watch/rules` 与 `POST /api/watch/requests`。
- “常用申请项”取启用的正积分规则，显示图标、规则名和积分值；点击后填充规则、标题、积分和说明。
- 图标优先按规则分类映射（学习、家务、运动、礼貌、习惯等），无法识别的分类使用通用星星图标；本期不要求新增规则图标字段或数据库迁移。
- 保留手工编辑申请事项、积分和说明以及提交后的最近申请状态跳转。

### 4.2 语音输入转文字

- 在“申请事项”和“说明”附近提供明确的麦克风按钮；点击开始识别，再次点击或识别结束后停止。
- 第一阶段采用浏览器/WebView 的 `SpeechRecognition`/`webkitSpeechRecognition`，语言为 `zh-CN`，识别结果只写入表单，仍由孩子确认后提交，不自动创建积分申请。
- 不支持语音识别、权限被拒绝、无网络或识别失败时，应显示可理解提示并保留键盘输入；不得阻断普通申请。
- Android WebView 壳实施时需同时验证麦克风权限链路：`RECORD_AUDIO` 声明、运行时权限申请、`WebChromeClient.onPermissionRequest` 仅允许当前受信任站点的音频请求。若目标手表 WebView 不提供语音识别能力，则需另立服务端转写方案，不能在本需求中假定平台兼容。
- 不持久化原始音频；本期无新增后端语音上传 API。

### 4.3 积分详情

- 复用 `GET /api/watch/score` 显示当前积分、现金、物品和更新时间，复用 `GET /api/watch/requests` 显示最近申请及状态。
- “积分详情”是只读页，不与首页重复承担导航功能；首页仍是默认落点。
- 状态至少区分待确认、已通过、已拒绝；长列表在表盘内容区纵向滚动，不产生页面级滚动。

### 4.4 好友

- “添加好友”复用 `POST /api/watch/friend-code` 和 `POST /api/watch/friends`，包含生成本人好友码、输入对方 8 位码、成功/失败反馈。
- “排行榜”复用 `GET /api/watch/friends` 返回的 `leaderboard`，独立展示名次、姓名、积分和“我”标识；空数据展示空状态。
- 现有好友列表可放在“添加好友”页下方，不在排行榜页重复展示。

### 4.5 设置

- “表盘设置”复用 `GET/PUT /api/watch/settings`，保留三款表盘和当前选中状态。
- “设备绑定”在已绑定设备中复用现有设备信息和解绑码流程；必须继续使用设备令牌与家长生成的一次性解绑码共同校验，不能提供仅凭设备令牌解绑的捷径。

## 5. 技术影响

### 5.1 前后端与数据

- 主要改动位于 `FamilyReward.Api/Program.cs` 中 `/watch` 的 HTML、CSS 和 JavaScript状态机。
- 现有积分、规则、申请、好友、表盘和设备 API 已覆盖本期数据需求，预计无需新增数据库表和后端业务接口。
- `watch-app/android/.../MainActivity.java` 可能因语音权限链路需要修改；`AndroidManifest.xml` 可能新增麦克风权限。仅在真机/目标 WebView 验证确有需要后实施最小权限。
- `watch-app/scripts/verify-watch-app.mjs` 必须新增菜单结构、图标、首页不变、页面跳转、语音降级和代表性视口的静态回归检查。

### 5.2 状态模型建议

建议将视图状态收敛为：`home`、`menu`、`points-apply`、`points-detail`、`friend-add`、`leaderboard`、`watch-face`、`device-binding`。菜单数据使用静态数组统一生成，避免 HTML 菜单与 JavaScript 跳转映射重复维护。

切换到各视图时按需拉取数据；首次绑定后的 `load()` 仍加载首页关键数据。请求失败只影响对应页面，并提供重试，不应使设备回到未绑定态，只有设备令牌返回 401 时才进入重新绑定流程。

## 6. 验收标准

1. 已绑定设备首次进入仍显示原首页，首页内容和表盘样式无回归。
2. 右侧在首页、菜单页和任一子页面始终只有一个“菜单”入口，不出现积分、申请、记录等展开按钮。
3. 菜单页一次展示六个带图标入口，并可清楚识别“积分/好友/设置”归属；所有入口均能进入正确页面并返回菜单。
4. 常用申请项均有图标；选择后正确带入申请内容，提交成功后家长端仍能收到并审批。
5. 支持的设备上可将中文语音转成申请文本，识别前后不会自动提交；不支持或拒绝权限时仍可手工输入。
6. 积分详情显示余额、更新时间和最近申请状态，数据与现有 API 一致。
7. 添加好友、排行榜、表盘设置、设备绑定/解绑能力行为与改版前一致，错误提示可见。
8. 页面在五组代表性视口及目标真机中无页面级横向滚动、无按钮裁切；需要滚动的菜单/详情/表单只在表盘内容区滚动。
9. 所有菜单按钮可通过可访问名称识别，图标不依赖外网资源。
10. `node watch-app/scripts/verify-watch-app.mjs`、ASP.NET Core 构建、相关 API 冒烟和目标手表真机回归均通过。
