# 干饭社交 V1

现有餐厅 ID、推荐结果和打卡历史继续作为分享入口，私有干饭档案与社交表分开。客户端只有进入「一起干饭」「我的饭圈」或选择历史记录中的分享时才读取社交数据。现有顶部入口和推荐不依赖新接口。

## 实施阶段

1. 临时饭局由发起人带入餐厅，使用随机 UUID 口令或二维码加入。口令对新成员有效期为 24 小时，结束后失效。结束与成员确认在同一饭局上串行；共同就餐统计只使用已经结束且双方都确认的饭局。
2. 共同就餐产生候选饭搭子，双方各自确认后才互相可见。后端在读取和互动时重新校验双方同意与单条动态范围，私人档案及餐厅坐标不进入社交接口。默认私人，公开范围未启用。收藏和想吃属于饭圈清单，列表只显示当前仍可见的来源。
3. 动态可带入原餐厅创建新饭局，并向互相确认的饭搭子发出站内邀请。邀请接收者可接受或拒绝，接受与加入同事务。后续接入跨设备身份展示、照片、社交推荐和固定组合识别。

## 验证和发布

使用 `host-build-output --project family-reward --target dining-social-regression -- bash scripts/check-dining-social.sh` 验证隔离 PostgreSQL 中的迁移重放、四人加入、UUID 大小写、幂等、权限变更、互动和邀请。测试身份方案只在测试入口编译，业务接口使用现有用户中心认证。

生产发布前先备份目标 PostgreSQL，经现有 Atlas 部署流程运行 `20261113-dining-gatherings-v1.sql` 和 `20261113-dining-social-v1.sql`。两份迁移仅新增表和索引，按文件顺序执行，由现有迁移脚本记录校验和。验证迁移记录及表结构后再启用对应服务和客户端。发布若需回退，先回退应用并保留新表以免丢失已写入的饭局或动态。

现阶段尚缺照片分享、发起饭局后改选餐厅、打卡成功页的直接分享、账号显示名和 P1 功能。真机四人扫码及发布后的真实权限验收仍需执行。
