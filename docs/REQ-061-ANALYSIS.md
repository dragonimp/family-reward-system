REQ-061 是 [REQ-060 付费动态表盘](./REQ-060-ANALYSIS.md)闭环中的家长 Web 端子范围：接收儿童手表创建的表盘使用申请、展示主题名称、唤起公共 pay 组件，并在可信支付成功后让服务端同步权益供儿童手表解锁。本需求不包含儿童端动画制作、商品运营后台或独立支付逻辑。

## 2. 现状与结论

当前家长 Web 仅有好友通知和积分业务页面；仓库没有表盘解锁申请、通用家长通知、表盘商品/权益、支付订单、公共 pay 组件客户端、支付回调或手表授权同步。因此 `TASK-223` 可凭本文和对应提交关闭，`REQ-061` 不可关闭。

“接收手表推送”应落为服务端业务事件，而不是浏览器与手表点对点通信：手表调用家庭积分 API 创建申请，后端持久化同一申请并通知有权家长；Web 通过通知接口拉取，或在平台具备能力时通过 SSE/WebSocket 收到变更提示后再查询详情。通知通道不可作为唯一事实来源，刷新页面必须能恢复未处理申请。

| 能力 | 可复用基础 | 仍需建设 |
| --- | --- | --- |
| 家长身份与孩子归属 | 现有家长鉴权、`child_user_bindings` 权限边界 | 表盘申请查询和付款接口必须复用同一归属校验 |
| 家长通知 | 好友通知具备查询、已读和所属家长过滤范式 | 新增表盘申请通知类型、状态、主题名和购买入口 |
| 表盘设置 | 手表已有静态主题偏好接口 | 商品目录、儿童权益和未授权主题服务端拒绝 |
| 支付 | 无 | 公共 pay 组件契约、服务端建单、可信回调/查单和幂等授予 |
| 状态同步 | 手表页面可重新读取服务端状态 | 支付成功后的权益落库、申请终态和手表刷新/轮询策略 |

## 3. 家长 Web 交互与状态

### 3.1 申请通知

1. Web 导航提供可发现的通知入口和未读数量；申请卡片至少展示孩子名称、表盘显示名称、服务端价格/币种、申请时间和当前状态。
2. 主题显示名称来自申请所引用的商品快照或服务端目录，不由 Web 根据主题键拼接；即使商品改名或下架，历史申请仍可审计。
3. 同一孩子、同一主题的活动申请只对应一条业务记录。多个有权家长看到的是同一申请状态，不复制成互相独立的付款申请。
4. 打开详情可标记通知已读，但“已读”不等于拒绝、取消或完成。付款成功前，申请保持可恢复状态。
5. 首期若无实时推送基础设施，可在进入页面、窗口重新聚焦和支付返回时刷新，并在支付处理中短时退避轮询；不得依赖永久高频轮询。

建议状态及操作：

| 状态 | 家长展示 | 可用操作 |
| --- | --- | --- |
| `pending` | 待解锁 | 去解锁 |
| `payment_pending` | 支付处理中 | 继续/查看支付结果；禁止无界重复建单 |
| `unlocked` | 已解锁，显示付款家庭成员和时间 | 无重复付款入口 |
| `cancelled` / `expired` | 已取消 / 已过期 | 按产品规则重新申请，不复用失效订单 |
| `payment_failed` | 支付未完成 | 在原申请下重试并创建受控的新支付尝试 |

### 3.2 唤起公共 pay 组件

1. 家长点击“去解锁”后，Web 先请求家庭积分后端创建支付会话；后端校验当前家长与孩子关系、申请状态、商品上架状态和服务端价格，再调用公共 pay 项目的正式应用接口。
2. Web 只把后端返回的短期会话令牌或跳转参数交给公共 pay 组件。支付 UI、支付方式、收单和支付凭据处理均由公共组件负责，本仓库不得复制支付表单或持有公共 pay 服务密钥。
3. 组件关闭、取消、失败、超时均返回可理解且可重试的状态，申请不丢失；组件初始化失败时保留“重新尝试”，不能显示已解锁。
4. 回跳参数、组件 `onSuccess` 或浏览器展示的成功页只能触发后端查单和界面刷新，不能直接写权益或把订单标记为已支付。
5. 若公共组件不支持当前 Web 技术栈，实施任务应只增加薄适配层；不得以“临时支付页面”绕过组件复用要求。

### 3.3 支付成功与手表授权同步

支付服务的验签回调或服务端主动查单是可信支付依据。家庭积分后端核对商户订单号、申请、商品、金额、币种和最终状态后，在同一事务中：

1. 幂等更新内部订单为已支付；
2. 为“孩子 + 表盘主题”写入唯一权益；
3. 将申请更新为 `unlocked`；
4. 记录可审计但不含支付凭据的事件；
5. 提交事务后发布授权变更通知。

“同步至儿童手表”不要求服务端远程强制切换当前表盘。在线手表可通过已有连接能力接收失效提示；无稳定推送能力时，手表在申请状态轮询、页面重新可见、打开表盘设置或重启后重新读取目录/权益。只要权益已在服务端提交，通知丢失也不能导致永久未解锁。手表切换接口仍必须在服务端校验权益，支付成功只解锁选择权。

## 4. 接口与安全边界

建议接口名称可按项目规范调整，但职责不可合并：

| 调用方 | 接口 | 责任 |
| --- | --- | --- |
| 家长 Web | `GET /api/watch-face-unlock-requests` | 按当前家长可管理的孩子查询申请、未读和支付状态 |
| 家长 Web | `POST /api/watch-face-unlock-requests/{id}/read` | 仅标记当前通知已读 |
| 家长 Web | `POST /api/watch-face-unlock-requests/{id}/payment-session` | 权限/状态/价格校验后创建公共 pay 会话，接受客户端幂等键 |
| 家长 Web | `GET /api/watch-face-unlock-requests/{id}` | 支付返回或轮询时读取服务端最终状态 |
| 支付服务 | `POST /api/payments/agent-pay/webhook` | 验签、去重、核单并在事务中授予权益 |
| 儿童手表 | `GET /api/watch/faces` | 重新读取主题目录、申请和权益状态 |

安全与一致性要求：

- 所有家长接口都从登录态解析家长身份并校验孩子归属；请求体中的家长 ID、孩子 ID、主题名、金额和币种均不能作为可信依据。
- 支付会话使用不可预测的内部订单号和幂等键；同一申请最多存在一个 `created/paying` 有效订单。多家长并发时由事务锁/唯一约束保证只有一笔可继续的业务订单。
- webhook 独立进行签名、时间窗和事件 ID 去重校验，不使用家长 Cookie 代替支付认证；无效签名、金额/币种不符、未知订单和乱序失败事件不得授予或回收权益。
- 不向 Web 返回服务密钥、完整支付凭据、回调签名或其他家长的个人信息；日志只记录脱敏订单关联和结果。
- 支付成功响应必须等待权益事务提交后再返回 `unlocked`，避免家长显示成功而手表查询不到授权。

## 5. 验收标准

1. 儿童手表确认申请后，有权家长刷新或收到变更提示即可看到申请；卡片准确显示孩子和申请的表盘名称，重复申请不产生重复通知。
2. 未登录、无孩子归属或其他家庭账号不能查看、标记已读、建单或查询该申请，统一返回 401/403/404 的既定安全响应。
3. “去解锁”只唤起公共 pay 组件；仓库没有自建支付方式或收集支付凭据的页面。组件收到的商品、金额和币种来自后端支付会话。
4. 组件取消、失败、初始化异常和超时均不授予权益；关闭后申请仍可查看和重试。
5. 伪造前端成功回跳、修改金额/币种、无效签名、未知订单、重复和乱序回调均不能错误授予权益。
6. 有效支付结果只生成一份“孩子 + 主题”权益；重复点击、多标签页和多家长并发不会产生重复有效订单或重复权益。
7. 支付成功后家长状态变为“已解锁”，其他有权家长看到相同终态；付款入口消失且页面刷新后状态保持。
8. 在线手表在目标同步时限内、离线手表在下次联网/打开设置时显示已解锁；无需重新绑定设备，且通知丢失可由重新查询恢复。
9. 未购买主题仍被 `PUT /api/watch/settings` 服务端拒绝；已购买主题可正常切换并在刷新、重启后保持。支付成功不擅自切换孩子当前主题。
10. 自动化至少覆盖家长权限、显示名称快照、建单幂等、支付失败、签名/金额篡改、回调重放、并发付款、事务回滚和手表重新查询；公共 pay 沙箱完成一次端到端验收。
