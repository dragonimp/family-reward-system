## 2. 问题与目标

REQ-053 当前实现把 24 项材料集中展示，并以“待补齐”为主要缺省状态，但资料包又把营业执照、法人证件、签名 APK、图标、介绍图、隐私政策、用户协议和性能报告等统称为“必须由发布主体提供”。该口径混淆了三件不同的事：

1. 材料是否敏感；
2. 材料最初由谁签发或产生；
3. 本项目是否已经能从受控系统读取，或能依据源码、既有资料和生产环境真实生成。

REQ-055 的目标是把上架工作区改为“系统主动补齐，用户只处理不可替代的外部动作”：

- 用户中心已有的个人凭证、测试账号和图灵软件主体资料，由系统按权限查询并引用，不重复索取或复制明文。
- 能从仓库、构建凭证、现有品牌素材和生产环境真实生成、验证的材料，由项目任务生成、上传并登记。
- 只有外部机构首次出具、平台本人验证码/协议签署/盖章，或物理目标真机才能产生且系统中尚无有效证据的事项，才进入“外部待办”。
- 每项材料都必须保留来源、版本、校验结果和上传/登记证据，不能仅由浏览器本地状态宣称完成。

## 4. 产品流程与状态口径

### 4.1 自动补齐流程

1. 创建发布包时锁定项目、平台、应用、包名、版本和源码提交。
2. 通过应用接口查询用户中心凭证、主体资料、项目资产和历史发布资产，只保存受控引用。
3. 对每份候选材料执行有效期、主体、应用名、包名、版本、尺寸、格式和授权范围校验。
4. 对缺失但可生成的材料创建项目任务：构建、验签、图片导出、文档生成、URL 发布或测试执行。
5. 将通过校验的材料上传至上架暂存区或目标平台草稿，并登记哈希、来源与回执。
6. 仅把系统无法取得或产生的真实证据汇总成外部待办，说明原因、所需动作、责任角色和截止时间。
7. 送审前重新检查短期凭证、线上 URL、签名、版本一致性和外部待办，不允许用手工勾选绕过失败项。

### 4.2 状态模型

每项材料至少区分：

- `discovered`：已找到候选资料，但尚未完成用途和有效性校验；
- `generated`：已由受控任务真实生成，尚未验证或上传；
- `verified`：内容、规格、主体、版本和授权校验通过；
- `uploaded`：已上传暂存区或目标平台草稿，并有回执；
- `registered`：资产及证据已绑定发布包，可参与送审校验；
- `external_action_required`：只能由外部机构、本人验证/签署或物理真机完成；
- `invalid`：资料过期、不一致、损坏、未授权或验证失败。

当前前端的 `prepared / missing / credential_configured / verified` 和 `localStorage` 只适合静态演示，不能作为真实上架状态源。实施时状态必须来自服务端发布包；浏览器不得自行把材料标为已上传或已登记。

### 4.3 安全与审计

- 个人证件、营业执照、keystore、密码、密钥和测试账号均使用受控资产/凭证引用，页面只展示脱敏摘要、状态和更新时间。
- 凭证读取必须校验项目、用途、操作者和执行任务权限；生成文件及日志不得包含密码、密钥、验证码或完整证件号码。
- 资产记录至少包含 `sourceType`、`sourceRef`、`contentHash`、`version`、`generatedByTask`、`verifiedAt`、`uploadedAt`、`receiptRef` 和 `expiresAt`。
- 资料变更后旧验证结果自动失效；发布包必须能追溯到源码提交、构建任务、文档版本和平台回执。
- 任何“未找到”都应记录查询范围和原因；禁止以空白文件、示例图片、模板、模拟测试或未签名 APK 冒充真实材料。

## 5. 功能与接口影响

### 5.1 用户中心与主体资料

项目管理应通过正式应用接口提供按当前用户/主体授权范围查询的能力，返回脱敏元数据和引用 ID。REQ-055 不要求在家庭积分仓库保存个人证件副本，也不允许上架任务直接读取生产数据库。

需要的逻辑能力包括：

- 查询当前用户可用于上架的个人凭证与测试账号引用；
- 查询图灵软件主体资料及营业执照、法人证件、软著、备案等资产引用；
- 验证凭证/资产用途授权、有效期和健康状态；
- 将已核验引用附加到指定发布包，并留下审计记录。

### 5.2 发布包与资产生成

现有 `docs/publishing/marketplace-release-tooling.md` 中的发布包、资产、凭证健康和规则快照对象可继续沿用，但需增加“发现/生成/校验/上传/登记/外部待办”编排，而不只是列出缺项。

建议提供以下幂等任务或接口：

- `resolve_marketplace_material_sources`：批量发现用户中心、主体和历史发布资产；
- `generate_marketplace_assets`：按材料类型触发构建、图片、文档或报告任务；
- `verify_marketplace_asset`：执行格式、主体、版本、签名、URL 和真实性校验；
- `attach_marketplace_submission_asset`：用受控引用和证据绑定发布包；
- `upload_marketplace_submission_assets`：上传暂存区/平台草稿并保存回执；
- `list_marketplace_external_actions`：只返回确实无法由系统完成的事项及原因。

生成、上传和送审必须是可重试、可审计的独立步骤。最终发布或生产部署仍由受控执行器完成，不由本任务 worker 执行。

### 5.3 上架准备页面

`/watch-release` 后续应展示“系统处理中、已复用、已生成、已验证、已上传、需外部动作、失败”及证据入口。页面不再把 21 项统一称为“待补齐”，也不允许仅通过下拉框和本地存储改变真实状态。

每个外部待办必须说明系统已经检查过什么、为什么不能自动完成、由谁执行、完成后提交何种回执。营业执照、法人证件等只有在系统未找到有效授权资料时才出现，而验证码、本人签署和真机证据可以直接标识为固有外部边界。

## 6. 验收标准

1. 创建小天才发布包后，系统通过应用接口查询用户中心个人凭证和图灵软件主体资料；已有有效营业执照、法人证件等被复用并绑定引用，不要求重复上传。
2. 查询过程不展示或记录密码、密钥、完整证件号码、验证码；未授权调用被拒绝并产生审计记录。
3. 对源码和现有资产可生成的签名 APK、签名摘要、148×148 图标、320×360 介绍图、隐私政策、用户协议和测试/性能报告，系统能创建真实任务并保存来源、版本、哈希和结果。
4. APK 必须验证包名、versionName、versionCode、签名证书和 SHA-256；未签名、签名不匹配或版本错误不得进入 `verified`。
5. 图标和介绍图通过格式、尺寸、数量、内容授权和隐私检查；示例图或不符合平台要求的截图不得登记为完成。
6. 隐私政策和用户协议的 HTTPS URL 可公开访问，线上正文与登记版本哈希一致，主体、功能、权限和儿童数据说明与真实实现一致。
7. 测试与性能报告包含真实环境、执行时间、工具/版本、样本、阈值、原始结果引用和结论；模板或模拟数字不计为报告。
8. 可自动处理的材料完成后被上传并登记到发布包，失败可重试且不会产生重复资产；每次上传均可查到平台/暂存区回执。
9. 外部待办清单只包含系统中缺失的外部机构证书/资质、本人验证码/签署/盖章和必须由物理真机产生的证据，并明确阻塞原因。
10. 上架页面状态来自服务端，刷新或换浏览器保持一致；前端本地状态不能改变发布包真实完整度。
11. 任一材料过期、主体/包名/版本不一致或来源资产更新后，系统撤销旧的通过状态并阻止送审。
12. 发布包全部必需材料达到平台规则要求且外部动作有真实回执后，校验才允许进入待送审；平台受理/上线仍需保存真实外部证据。
