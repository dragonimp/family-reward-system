# family-reward-REQ-067 亲子双向成长调整需求分析

## 事项与结论

- Orbit 任务：`gpt_c4eacf8b958849f7afee751991f252ee`
- 需求：`family-reward-REQ-067`（`f5eb49bd-43cf-42c5-94b0-cc32567286b7`）
- 分析任务：`family-reward-TASK-247`（`7be34781-1e50-41cf-8870-e8b0c40f11ae`）
- 类型：V0.8 基线后的产品变更
- 功能点：`fc29caf0-452c-4546-9fc3-2be2fb68d1e0`

本需求不是对积分功能换皮，而是在保留现有积分交易模型的同时增加一条独立的“成长事实—总结—报告”链路。暖心内容不产生积分、不进入余额、分类统计或任何排行；报告只比较同一主体在不同时段的变化，不做孩子之间、家长之间或家庭之间的横向评价。

当前仓库已冻结 [V0.8 基线](./releases/V0.8.md)，但尚无暖心记录、AI 总结、成长报告和每日简报数据模型；`/watch` 仍直接展示好友排行榜，Web `Stats` 仍将孩子按积分排序并相互比较。因此 `TASK-247` 可凭本文和对应提交关闭，`REQ-067` 仍须保持待开发，不能以需求分析完成代替功能交付。

## 目标与非目标

### 必须实现

1. 保留现有 `transactions`、账户余额、记分申请和审批行为，迁移不得改写历史流水。
2. 手表首页增加“暖心时刻”入口。已绑定孩子先从有权记录的家庭家长中选择一人，再用文字或语音转写输入一条客观事实，确认后提交。
3. 每个家庭日按家庭时区为收到记录的家长生成一份暖心总结；没有事实时不编造总结，可明确显示“今天还没有暖心记录”。
4. 孩子端和家长端提供日、周、月报告，均包含“做得好的点”“接下来可以试试”“变化总结”，并能逐条追溯到获授权的原始记录。
5. 手表提供轻量每日简报；Web 统计默认展示同一主体本期与其过去可比周期，不默认展示横向排名。
6. 好友排行榜默认关闭；即使用户以后主动开启，暖心记录、总结和报告也永远不得成为排行输入或排行内容。

### 明确不做

- 不为暖心内容增加积分、徽章、星级、分项分数、完成率或排名。
- 不输出“好孩子/坏家长”、人格归因、心理诊断、疾病风险或确定性教养结论。
- 首版不做开放评论、公开动态、好友分享、自动奖惩或由 AI 直接修改积分。
- 首版不保存原始音频；语音只作为输入方式，用户确认转写文本后提交。若后续确需留存音频，必须另立隐私与合规需求。

## 角色、可见范围与核心流程

### 权限

| 角色 | 可写 | 可读 |
| --- | --- | --- |
| 已绑定孩子 | 为自己绑定关系内、当前家庭可见的家长记录暖心事实 | 自己提交的原始记录；面向自己的报告和简报；授权给自己的家庭摘要 |
| 家长 | 首版不代孩子创建“孩子视角”记录，可补充仅自己可见的更正备注 | 以自己为对象且属于有权家庭的记录、自己的总结，以及名下孩子获授权的报告 |
| 圈子成员/好友 | 无 | 无；加入圈子或成为好友不自动获得暖心内容权限 |

家长候选不能简单读取所有 `household_members`。服务端必须从当前手表绑定的孩子、孩子与家长绑定关系、当前家庭成员关系求交集，并只返回稳定 ID、显示名和与孩子的关系称谓。客户端传来的家长 ID、家庭 ID和记录者 ID都必须重新校验，不能据此越权。

### 手表记录流程

1. 首页进入“暖心时刻”，读取可选择家长；无候选时给出可恢复提示，不允许自由输入一个未绑定对象。
2. 选择家长后进入输入页，可键入文字，或调用现有语音能力取得临时转写文本。
3. 转写失败时保留文字输入；提交前必须显示完整文本供孩子确认、修改或取消。
4. 服务端保存原始文本、对象、记录者、家庭日、来源和时间。建议单条 1～500 个 Unicode 字符，去除纯空白，使用幂等键避免弱网重复提交。
5. 成功后只反馈“记录好啦”，不显示加分、星级或质量评价。

### 总结与报告流程

- 日总结任务按家庭配置的 IANA 时区划分日期，默认执行时刻建议为当地 21:30；允许次日补偿和人工重试，同一对象/周期/模板版本必须幂等。
- 生成前先按主体、家庭和周期取有权限的原始事实；提示词要求事实归纳、温和建议和不确定性表达，并禁止诊断、打分、比较和虚构。
- 模型输出先经过结构校验与禁用表达检查。失败时保留原始事实并标记可重试，客户端不得把失败包装成成功总结。
- 日/周/月报告使用相同的版本化快照机制。周建议以周一至周日、月以自然月为默认口径；变化总结只能比较该主体的相邻可比周期，并注明样本不足。
- 每个报告段落保存引用记录 ID。界面点击引用可打开原始记录；原始记录被依法删除或撤回后，引用显示“原记录已不可用”，不得泄露缓存正文。

## 建议数据模型

暖心链路使用独立表，不给 `transactions` 增加复用字段：

| 实体 | 关键字段 | 约束 |
| --- | --- | --- |
| `warm_moments` | `id`、`family_group_id`、`author_child_profile_key`、`subject_parent_app_user_id`、`content`、`input_mode`、`occurred_on`、`family_timezone`、`idempotency_key`、`created_at`、`deleted_at` | 对象和作者必须有有效家庭关系；`input_mode` 仅 `text/stt`；内容不含分数；幂等键按作者唯一 |
| `growth_reports` | `id`、`family_group_id`、`subject_type`、`subject_key`、`period_type`、`period_start/end`、三个结构化段落、`status`、`model_provider/model_name`、`prompt_version`、`generated_at` | 主体与周期唯一；内容是快照；允许 `pending/generated/failed` |
| `growth_report_sources` | `report_id`、`warm_moment_id`、`sort_order` | 建立报告到事实的可追溯引用，不复制原文作为排行数据 |
| `family_growth_settings` | `family_group_id`、`timezone`、`friend_leaderboard_enabled`、`report_schedule`、`updated_by/at` | 排行开关默认 `false`；旧家庭迁移也必须显式回填 `false` |

若孩子报告后续还需要引用积分交易，应增加通用的报告来源类型和经授权的交易引用，而不是把暖心事实伪装成交易。AI 请求/响应日志只记录排障所需元数据与脱敏错误，默认不记录完整未成年人文本。

## API 与界面边界

建议以版本稳定、权限清晰的资源接口实现：

- `GET /api/watch/warm-moments/parents`
- `POST /api/watch/warm-moments`
- `GET /api/watch/daily-brief?date=YYYY-MM-DD`
- `GET /api/growth-reports?subjectType=&subjectKey=&periodType=&periodStart=`
- `GET /api/growth-reports/{id}`（含用户有权读取的来源摘要）
- `GET /api/warm-moments/{id}`（从报告追溯原始事实）
- `GET/PUT /api/family-groups/{id}/growth-settings`

Web 应新增成长报告入口，并把 `Stats.tsx` 的默认视图改为“自己与过去比”：先选择主体和日/周/月周期，再展示本期值、上个可比周期和变化说明。现有积分排行如继续保留，应移入明确的可选区域并受家庭开关控制。手表现有 `data-view="leaderboard"` 菜单同样受服务端开关控制，默认不渲染；不能仅用前端 CSS 隐藏。

每日简报在小屏只显示三个短段落和“查看记录”数量，长内容按句安全截断并允许翻页；不得在手表通知或锁屏预览中默认展示具体暖心原文。

## AI、安全与隐私护栏

1. 生成输入按最小必要原则选择，必须带数据区域、供应商、保留期和未成年人数据处理配置；不得用业务内容训练公共模型。
2. 提交前向孩子展示适龄提示：不要记录住址、电话、学校班级、密码、医疗信息等敏感内容。服务端做长度、恶意内容和明显敏感信息检查，但不能因自动过滤失败而扩散原文。
3. 输出采用结构化 schema，三个段落均为文本加来源 ID；来源不存在时禁止模型自行补足事实。
4. 禁用表达至少覆盖星级、分数、名次、好坏标签、心理/医学诊断和主体间比较；自动检查是兜底，提示词、评审样例和人工抽检同样必需。
5. 删除、导出、保留期、监护人同意、孩子适龄告知和 AI 供应商条款须在开发验收前形成产品口径。删除必须同步影响搜索、报告引用和后续生成语料。
6. 排行查询的数据源白名单只能包含既有积分账户/交易派生数据；`warm_moments`、`growth_reports` 及其来源表不得 JOIN 到排行路径。

## 实施拆分与依赖

建议按以下可独立验证的任务推进，每组完成后提交：

1. 数据迁移、家庭时区/排行开关、暖心记录权限与 API。
2. 手表家长选择、文字/STT 确认、提交和弱网幂等。
3. 版本化 AI 生成器、日调度、补偿重试、结构/安全校验和来源引用。
4. Web 日/周/月报告、原始记录追溯、删除/撤回和个人历史比较统计。
5. 手表每日简报、排行榜默认关闭与所有排行数据源隔离。
6. 权限、隐私、生成质量、旧积分回归、目标 WebView 和受控部署后线上验证。

以下产品/环境决定不阻塞本次分析完成，但在对应开发进入验收前必须确认：

- STT 与大模型供应商、数据区域、合同/训练选项、超时和成本上限；无可用供应商时允许只交付文字记录与“待生成”状态，不能用假总结替代。
- 家庭时区来源、每日生成时刻、周起始日，以及报告最少事实数量。
- 监护人同意、孩子告知、原始记录/报告/生成日志的保留期、导出与删除 SLA。
- “孩子端报告”的具体载体是手表完整报告、每日简报入口还是后续独立儿童端；本分析按手表只承载每日简报、Web 承载完整报告估算。
- 旧家庭的好友排行是否提供一次性迁移提示；无论提示形式如何，数据库默认值必须是关闭。
